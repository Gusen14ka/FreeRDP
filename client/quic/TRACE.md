# Трассировщик PDU (RDP_TRACE)

## Зачем

Цель — сравнить транспорты (TCP, QUIC с одним потоком, QUIC с потоками по
каналам) на одинаковой нагрузке и одинаковой сети. Живой RDP для этого
неудобен: xrdp подстраивается под сеть, и при разных транспортах сервер
шлёт разные данные. Поэтому нагрузка **записывается один раз** на идеальной
сети (клиент и xrdp на одной машине), а потом **проигрывается** через разные
транспорты с помехами (netem).

Трасса — это запись всех PDU одной RDP-сессии: когда, в какую сторону,
в какой поток форка и сколько байт. PDU (Protocol Data Unit) — одно целое
сообщение RDP. Содержимое PDU не пишется: транспорту важны только размер и время.

## Где встроен и почему именно там

FreeRDP читает и пишет сеть через таблицу функций транспорта
`rdpTransportIo`. Две из них работают с **целыми PDU уже после TLS**:

- `ReadPdu` — прочитать из сети одно PDU (сервер → клиент);
- `WritePdu` — отправить одно PDU (клиент → сервер).

Ровно эти две функции подменяет и QUIC-режим форка (`quic_transport.c`,
модуль прокси `quicmux`). Трассировщик подменяет их же, но не меняет
передачу: обёртка вызывает стандартную функцию и записывает строку о PDU.
Соединение остаётся обычным TCP.

Так **единицы трассы совпадают с единицами воспроизведения**: плеер QUIC
кладёт каждую строку в поток её канала, QUIC single — всё в один поток,
TCP — всё подряд. Ничего не нужно угадывать или пересобирать.

```
xrdp ──TCP+TLS──> [TLS] ──> ReadPdu ──> обёртка trace_read_pdu ──> FreeRDP
                                              │
                                              └─> строка в CSV
```

## Классификация: quic_classify.h

Чтобы трасса делила поток так же, как форк, классификатор один на всех:
клиент форка, quicmux и трассировщик включают `quic_classify.h`.

| Поток | Что туда попадает |
| --- | --- |
| `graphics` | обновления экрана и курсора (fast-path от сервера; slow-path DATA/UPDATE, DATA/POINTER) |
| `input` | ввод (fast-path от клиента; slow-path DATA/INPUT) |
| `vchannel` | всё на MCS-каналах, кроме основного (звук `rdpsnd`, буфер обмена `cliprdr`, `drdynvc`, `rdpdr`) — целиком, чтобы не нарушить порядок внутри канала |
| `control` | подключение, лицензирование, синхронизация и всё, что не удалось разобрать |

**Исправленная ошибка (коммит с quic_classify.h).** Прежний разбор считал,
что после MCS всегда идёт security header, а длина MCS всегда 2 байта, и
читал тип данных со сдвигом на байт. При TLS security header у данных нет,
поэтому поле длины читалось как флаги безопасности, и обновления экрана
уходили в `control`. С xrdp 0.9.24 + TLS это почти вся графика (на стенде:
~75 000 PDU slow-path против 7 fast-path). Теперь наличие security header
определяется по данным: Share Control header узнаётся по совпадению
`totalLength` с остатком PDU и корректному `pduType`.

## Формат файла (trace v1)

```
# trace v1
# start_unix_ns=1792341366984569549          реальное время старта
# host=127.0.0.1:3389 size=1280x720 bpp=32   параметры подключения
# scenario=test_testsrc2 run=1 image=...     RDP_TRACE_META от скрипта
t_us,dir,stream,mcs,len
39136,u,control,,45
...
# mcs 1003=io                                номера каналов -> имена
# mcs 1005=rdpsnd                            (пишутся после подключения)
...
# end pdus=86509 write_len_mismatch=0        признак штатного закрытия
```

| Столбец | Смысл |
| --- | --- |
| `t_us` | микросекунды от открытия трассы, монотонные часы (не прыгают при подводке времени) |
| `dir` | `d` — сервер → клиент, `u` — клиент → сервер |
| `stream` | поток форка (таблица выше) |
| `mcs` | номер MCS-канала; пусто у fast-path и пакетов до MCS (X.224, MCS Connect) |
| `len` | размер PDU в байтах |

Чтение: `pandas.read_csv(path, comment='#')`.

Особенность виртуальных каналов: RDP режет их сообщения на куски по 1600
байт (chunk), в трассе видны именно куски. Звуковой блок xrdp — 7 строк:
38 + 5×1623 + 215 байт.

## Включение

```bash
RDP_TRACE=/путь/trace.csv \
RDP_TRACE_META="scenario=... run=..." \
xfreerdp /v:... /u:... ...
```

Без `RDP_TRACE` код ничего не делает. В `xfreerdp-quic` трасса не пишется:
QUIC-транспорт ставит свои `ReadPdu`/`WritePdu` позже и заменяет обёртки.

## Файлы

| Файл | Что делает |
| --- | --- |
| `quic_classify.h` | классификация PDU по потокам, номер MCS-канала; header-only, без FreeRDP |
| `quic_trace_writer.{h,c}` | запись CSV: буфер 1 МБ, сброс раз в секунду, мьютекс для многопоточности; без FreeRDP |
| `quic_trace.{h,c}` | обёртки `ReadPdu`/`WritePdu`, метаданные, имена каналов |
| `quic_input_script.{h,c}` | формат файла ввода: разбор и запись строки; без FreeRDP |
| `quic_input.{h,c}` | запись и воспроизведение ввода: обёртки `rdpInput`, поток воспроизведения |
| `../X11/xf_client.c` | вызовы трассировщика и модуля ввода:: `quic_trace_pre_connect` (PreConnect), `quic_trace_post_connect` (PostConnect), `quic_trace_close` (PostDisconnect) |
| `tests/` | unit-тесты классификатора и записи |

## Надёжность записи

- **Не тормозит клиент.** Строка (~30 байт) копируется в буфер в памяти, на
  диск уходит пачками. Проверено на стенде чередованием прогонов с записью и
  без: разница ~1 % при разбросе между прогонами 3,8 %.
- **Полнота.** Сумма `len` всех PDU сервера против счётчика байт сетевого
  интерфейса контейнера — 98,7 % (остальное — заголовки TLS и TCP/IP).
- **Убийство клиента.** SIGTERM (обычный `kill`) обрабатывается FreeRDP
  штатно — файл закрывается со строкой `# end`. При `kill -9` теряется не
  больше ~1 с хвоста (сброс буфера раз в секунду).
- **Диагностика.** `write_len_mismatch` считает случаи, когда
  `Stream_Length` ≠ позиции потока при записи (форк в QUIC-режиме берёт
  длину из `Stream_Length`). На стенде — 0.

## Запись и воспроизведение ввода (RDP_INPUT_RECORD / RDP_INPUT_SCRIPT)

Зачем: в синтетических трассах нужен ввод как у человека — с живым ритмом,
но одинаковый от прогона к прогону. Поэтому ввод не придумывается, а
записывается с человека и потом воспроизводится.

```bash
RDP_INPUT_RECORD=/путь/input.csv xfreerdp ...   # работаешь руками — ввод пишется
RDP_INPUT_SCRIPT=/путь/input.csv xfreerdp ...   # тот же ввод воспроизводится
```

Обе переменные можно задать сразу: в RECORD попадёт то, что реально
отправил проигрыватель (так проверяется точность воспроизведения).

### Где встроено

Ввод в FreeRDP идёт через таблицу функций `rdpInput` (`KeyboardEvent`,
`MouseEvent`, ...). Обработчики клавиатуры и мыши xfreerdp вызывают
`freerdp_input_send_*()`, а те — функции из этой таблицы.

- **Запись** — обёртки над функциями таблицы: записать событие и вызвать
  оригинал. Запись идёт внутри клиента, уже после того как xfreerdp
  захватил клавиатуру, поэтому захват ей не мешает (в отличие от внешних
  рекордеров макросов).
- **Воспроизведение** — отдельный поток вызывает те же
  `freerdp_input_send_*()` с записанными аргументами. Всё ниже этой
  функции — формат PDU, размер, путь через транспорт — то же, что у
  живого нажатия.

**Тонкость.** FreeRDP заполняет таблицу ввода при обмене возможностями
(Confirm Active) — уже после `PostConnect` — и заполняет заново при каждой
реактивации сессии. Поставить обёртки один раз нельзя: их затрёт. Поэтому
модуль оборачивает `WritePdu` транспорта (как трассировщик) и на каждом
исходящем PDU проверяет таблицу: если там не наши функции — запоминает
новые оригиналы и ставит обёртки снова. Первые PDU после регистрации ввода —
служебные (Synchronize, Control), так что обёртки на месте до первого
нажатия. Момент первой установки = активация сессии = ноль времени и для
записи, и для воспроизведения.

### Формат файла

```
# input v1
# size=1280x720                 координаты мыши верны только для этого размера
t_us,type,flags,a,b
8314793,kbd,0x0000,18,0         клавиша 'e' нажата (скан-код 18)
8344420,kbd,0x8000,18,0         отпущена (флаг RELEASE)
10500000,mouse,0x0800,600,400   мышь в точку (600, 400)
# end events=51
```

| `type` | что это | `a`, `b` |
| --- | --- | --- |
| `kbd` | клавиша по скан-коду | код, — |
| `unicode` | символ Unicode | код символа, — |
| `mouse` | движение, кнопки, колесо | x, y |
| `xmouse` | доп. кнопки мыши | x, y |
| `relmouse` | относительное движение | dx, dy |
| `sync` | состояние Caps/Num/Scroll Lock | —, — (всё во `flags`) |
| `focus` | окно получило фокус | —, — |
| `pause` | клавиша Pause | —, — |

`flags` — флаги RDP в том виде, в каком их получает `freerdp_input_send_*()`.

### Проверка (песочница с xrdp)

Ввод имитировался `xdotool` через X11 в окно xfreerdp — тот же путь, что
у настоящей клавиатуры: набор строки, Enter, клик, прокрутка колесом.

| | запись | воспроизведение |
| --- | --- | --- |
| событий (без `focus`) | 48 | 48 — тип, флаги, коды и координаты совпадают |
| расхождение времени | — | медиана 0,16 мс, максимум 0,28 мс |
| PDU ввода в трассе | 51 (по одному на событие) | 53 |
| ответ сервера (графика в окне набора) | 22 PDU, 1403 байта | 22 PDU, 1403 байта |

Два лишних PDU при воспроизведении — события `focus`: при старте их шлёт
и сам xfreerdp, и проигрыватель повторяет записанные. Это 8-байтные пакеты,
на нагрузку не влияют.

### Ограничения

- Состояние экрана при старте должно совпадать с записью (чистый
  контейнер, одинаковый запуск приложений): клик в точку попадает в нужную
  кнопку, только если окно стоит там же.
- События идут по абсолютному времени и не ждут реакции сервера
  (на идеальной сети записи это почти не важно).
- Голос с микрофона этим модулем не записывается — для его повтора нужен
  отдельный виртуальный источник звука на клиенте.

## Тесты

```bash
sh client/quic/tests/run_tests.sh
```

Не требуют сборки FreeRDP, собираются с AddressSanitizer/UBSan (ловят
выход за границы буфера и неопределённое поведение).

- `test_classify.c` — 16 случаев по спецификации, включая реальный заголовок
  PDU от xrdp с TLS, и 1 млн случайных буферов.
- `test_trace_writer.c` — 200 000 записей из 4 потоков: ничего не потеряно,
  не перемешано, время в каждом потоке не убывает.
- `test_input_script.c` — разбор правильных и испорченных строк файла ввода,
  100 000 случайных событий «записал → прочитал» без потерь.

## Ограничения

- Воспроизведение трассы — **без обратной связи** (open-loop): плеер шлёт PDU
  по записанному расписанию и не реагирует на сеть, а живой xrdp
  подстраивался бы. Это нужно указать в методике.
- Время — момент чтения PDU клиентом. На идеальной сети это почти момент
  отправки сервером, но только пока клиент не перегружен (поэтому клиент
  запускается на отдельных ядрах).
- Тип сообщения внутри канала (звуковой блок, подтверждение) не пишется;
  его можно восстановить по размерам (см. trace_check.py на стенде).
